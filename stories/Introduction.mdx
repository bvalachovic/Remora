## Installing in an app

### 1 — Point npm at the GitLab registry

Add a `.npmrc` to the consuming project root:

```ini
@platform:registry=https://gitlab.yourcompany.com/api/v4/packages/npm/
//gitlab.yourcompany.com/api/v4/packages/npm/:_authToken=${GITLAB_NPM_TOKEN}
```

Set `GITLAB_NPM_TOKEN` as an env var or CI/CD secret (use a GitLab Deploy Token with `read_package_registry` scope).

### 2 — Install

```bash
npm install @platform/design-system
```

> **Lit is a peer dependency.** Install it once per app if not already present:
> ```bash
> npm install lit
> ```

## Usage by framework

### Plain HTML

```html
<script type="module">
  import '@platform/design-system';
</script>

<ds-user-profile id="profile"></ds-user-profile>

<script type="module">
  const el = document.getElementById('profile');
  el.user = await fetchOktaUser(userId);   // assign as a JS property
</script>
```

### React (18)

```jsx
import '@platform/design-system/user-profile';

function Header({ oktaUser }) {
  return (
    <ds-user-profile ref={(el) => { if (el) el.user = oktaUser; }} />
  );
}
```

> React 19+ supports Custom Elements natively. For React 18 set object properties via `ref`.

### Vue 3

```vue
<script setup>
import '@platform/design-system/user-profile';
</script>

<template>
  <ds-user-profile :user="oktaUser" />
</template>
```

### Angular

```ts
// app.module.ts
import { CUSTOM_ELEMENTS_SCHEMA } from '@angular/core';
@NgModule({ schemas: [CUSTOM_ELEMENTS_SCHEMA] })
export class AppModule {}
```

```html
<!-- template -->
<ds-user-profile [user]="oktaUser"></ds-user-profile>
```

## Does my app need TypeScript?

**No.** The package ships pre-compiled JavaScript. TypeScript was used to *author* the components but plays no role at runtime.

| App type | What you get |
|---|---|
| **JavaScript app** | Components work as-is. No TypeScript config needed. |
| **TypeScript app** | Full type definitions ship with the package. You get editor autocomplete for `OktaUser`, `OktaUserStatus`, etc. automatically. |

```ts
// TypeScript apps can import types directly:
import type { OktaUser } from '@platform/design-system';
```

## Full library or one component?

You have two import styles. Both work with any bundler.

### Import the whole library

```js
import '@platform/design-system';
// or with a named export:
import { UserProfile } from '@platform/design-system';
```

The package ships as **ES modules with one file per source module**. Modern bundlers (Vite, webpack 5, Rollup, esbuild) will automatically **tree-shake** anything you don't import — so only the components your app actually uses end up in your final bundle.

### Import a single component directly

```js
import '@platform/design-system/user-profile';
```

Each component has its own sub-path export. This is the most explicit option and requires zero bundler intelligence — it's ideal for CDN usage or environments without a build step.

<div class="callout">
  <strong>Bottom line:</strong> for most apps the full-library import is simpler and the bundle difference is negligible. Use the sub-path import when you want to be explicit or skip a bundler entirely.
</div>

## This Storybook site

This site is the live design system documentation. It can be built as a static site and deployed anywhere (GitLab Pages, S3, Nginx):

```bash
npm run build:storybook   # outputs to storybook-static/
```

Every component in the library has its own story page showing:

- **All visual states** — sizes, data variations, edge cases
- **Interactive controls** — change props live in the browser
- **Accessibility audit** — the Accessibility tab on every story runs axe-core (WCAG 2.1 AA) automatically and flags violations

---

## Accessibility

Every component is built to **WCAG 2.1 Level AA**. The Storybook Accessibility panel (powered by [axe-core](https://github.com/dequelabs/axe-core)) runs on every story automatically — check the **Accessibility** tab in the panel below any story to see the audit results.

Specifically enforced rules:

| Rule | Why |
|---|---|
| `color-contrast` | 4.5:1 minimum for normal text, 3:1 for large text |
| `button-name` | Every interactive element has an accessible name |
| `image-alt` | Decorative images use `alt=""` (WCAG 1.1.1) |
| `aria-*` validity | ARIA roles and attributes are used correctly |

Keyboard behaviour is tested in stories via the browser's built-in focus management — components use native `<button>` elements so that Tab, Enter, Space, and Escape work without custom key handling.

## Theming

Override CSS custom properties in your app's global stylesheet. No shadow DOM piercing required.

```css
:root {
  --ds-font-family: 'Inter', sans-serif;
  --ds-focus-color: #0052cc;   /* matches your brand focus ring */
}
```

| Property | Default | Controls |
|---|---|---|
| `--ds-font-family` | system-ui | Font inside all components |
| `--ds-focus-color` | `#6366f1` | Focus ring on interactive elements |

## Contributing

See the **Development** section of the [README](https://gitlab.yourcompany.com/platform/design-system/-/blob/main/README.md) for the full guide. The short version:

1. Create `src/components/<name>/` with `.component.ts`, `.styles.ts`, and `index.ts`
2. Export from `src/index.ts` and add a sub-path in `package.json`
3. Write stories in `stories/<Name>.stories.ts` covering all states
4. Run `npm run type-check` before opening a merge request
